## 三类工作负载，不能只看GPU忙不忙

策略更新做批量前向/反向，采样逐步生成，评分可能是模型推理、CPU程序或外部执行。它们的算存、长度和延迟分布不同。HybridFlow/verl把这些角色及通信、重分片与编排作为核心问题；它是实现参考，不是本项目已经运行的框架。[1]

| 模块 | 关键交接物 | 最小可观测量 |
| --- | --- | --- |
| trainer | 新权重版本、优化器进度 | 成功更新数、有效目标数、step时间 |
| rollout worker | 轨迹与行为概率 | 生成长度分位数、截断率、版本年龄 |
| reward / verifier | 评分与状态 | 完成/失败/超时数、版本 |
| queue / coordinator | 批次成员和同步确认 | 队列深度、丢弃/重试、版本分布 |

角色可以共用硬件，也可分离。colocated可能减少资源切换/通信中的某些成本，disaggregated可以独立扩缩，但引入传输、排队与陈旧度；不能无条件说哪种更快。

## 先保持学习语义，再安排GPU

接着1.3的**2题×4回答=8轨迹、28有效位置、2个epoch、4次actor更新**算例，假设有8台逻辑设备，选择一种独立设计的布局：

```text
learner池： GPU0──TP──GPU1     GPU2──TP──GPU3
            DP副本0            DP副本1
                 ↖ 同一TP位置之间的DP梯度同步 ↗

rollout池： GPU4  GPU5  GPU6  GPU7（4个单卡采样副本）
                   ↑ 权重导出/重新分片/版本确认
reward/工具：独立服务或CPU程序；队列/日志/检查点共享身份
```

此例训练池4设备=DP2×TP2，数据副本是2；每个全局mini-batch4条，各DP副本2条，每次微批次1条就累积2次后更新。不是“8卡各1条所以batch8”，也不能把两个TP切片再当两份数据。每epoch两次更新，两个epoch共4次；原28目标位置被学习两遍，共56次有效位置消费，不等于生成了56个新动作。

实际选择还取决于模型是否单卡放得下、互联和激活/KV开销。本图没有启动8GPU，也不是可直接导入的框架配置。[HybridFlow](https://arxiv.org/html/2409.19256v2)说明训练和生成可以采用不同并行布局；本图采用自编设备号，只解释交接。

| 技术 | 对哪个对象起作用 | 与算法衔接时必须保持什么 |
| --- | --- | --- |
| DP/DDP | 多份数据副本聚合梯度 | 全局样本/目标分母与同步次数 |
| FSDP/ZeRO | 分片参数、梯度或优化器状态 | 参数可见性、重组、分布式保存与全局范数 |
| TP | 切分单层张量计算 | 层内通信与生成端的权重布局转换 |
| PP | 不同设备执行不同层段 | 微批次调度、流水空泡及实际更新边界 |
| 重计算/高效attention/packing | 改变激活、kernel或批次组织 | 因果范围、动作mask、样本边界和原目标权重 |

这里的训练/生成分工不是部署知识扩展，而是后训练自身的执行路径。角色数、模型份数、进程数、设备数和数据副本数分别计量。MoE/CP等可继续读框架材料，本书此处先完成可复核的接口，不强行堆成固定“几维并行”配方。

### 一个mini-batch怎样跨微批次和rank归一化

另取一个独立的固定窗口子例，优化有效token平均：两个rank各处理一条窗口，分别有2与4个有效位置，总分母6；它不是上面8轨迹布局的原批次。默认DDP平均两个rank梯度，各rank应对**本地loss总和乘2/6**后反传；不能各自除2或4再平均。若原算法定义按回答等权，就先算每条回答内部均值，再按全局回答数归约，不能擅自换成token平均。[DDP文档](https://docs.pytorch.org/docs/2.11/generated/torch.nn.parallel.DistributedDataParallel.html)

完整顺序为：清梯度 → 按同一全局目标累计微批次 → 需要的梯度归约 → AMP情形每优化器一次unscale → 全局语义的梯度范数裁剪 → 实际成功更新 → 相应计数与调度。DDP完整副本可在同步后裁剪；参数分片时须用该分片实现支持的全局范数机制，不能对每个局部分片独立clip就宣称等价。[AMP累积与裁剪](https://docs.pytorch.org/docs/2.11/notes/amp_examples.html)

FP16 GradScaler可能跳过含非有限梯度的优化器更新；支持BF16并不意味着必须启用同样的loss scaling。actor/critic可有独立优化器和成功计数，不能假设同时成功。调度若按成功更新推进，就只在对应成功时推进；若按消费token推进，要另说明跳过时如何计量。发布actor版本不能假装发生了未执行的权重更新。

## 同步需要可确认的边界

假设训练从v10到v12，只有部分worker确认加载v12，下一批就必须标明实际采样版本。不能只在trainer日志写“已同步”就推定所有轨迹一致。完整恢复若包含异步队列，还要决定在途轨迹是重放、丢弃还是迁移，以及old logp与评分身份如何保留。

原第6章默认实验同步串行，每轮采样后做规定更新，没有生产队列。新增生命周期夹具与可选两rank数值子例的范围在6.4单独列出；它们不构成verl生产容错或GPU验收。

### 梯度同步与权重同步是两个过程

**梯度同步**发生在同一次分布式优化中，决定如何形成一个全局参数步。**权重同步**把某次已更新actor交给采样引擎，还可能涉及分片导出、跨进程传输、原子切换和加载确认。critic、优化器矩不需要一并送给rollout。

权重相同也不保证KV cache可沿用：cache是指定权重在指定前缀上计算的中间状态。若在长回答中途切换权重，通常要重算相关前缀KV；还要记录不同片段实际由哪版策略生成，不能只存一个“结束时版本”。AReaL的可中断生成和陈旧度控制有专门算法约定，不是给普通PPO加一个后台线程。[4，§4–5]

## 队列、长尾和背压怎样影响学习分布

同步批次等待长回答，短回答worker可能空闲；异步可让已完成经历先进入训练，却增加版本差异。若总优先收短任务，优化器看见的难度/长度分布也可能改变。用队列追求忙碌率之前，要保存各任务来源、等待、超时与拒绝原因。

假设生产者每秒完成60条、learner每秒接收40条，若持续30秒且没有其他变化，就净增600条等待；这只是确定速率算例，不是硬件性能。队列上限、任务背压、最长数据年龄和超时处置应一起设定。盲目扩采样卡会积累更老的数据，不一定增加有效训练进度。

| 从请求到更新 | 最小协议 | 对算法有什么影响 |
| --- | --- | --- |
| 提交请求 | task/request/attempt ID，分支预算 | 采样机会与题目分布 |
| 完成/失败 | 自然EOS、截断、工具异常分别记 | 奖励与价值边界 |
| 评分/筛选 | 评分版本、保留理由、原始回报 | 过滤后的实际分布与分母 |
| 接收入批 | 行为版本、年龄、重复消费策略 | ratio、陈旧度与复用预算 |
| 成功更新 | committed batch、actor更新数 | 去重、调度、发布和恢复边界 |

本节默认“一个batch只提交一次”是协议选择；有意重放必须另计reuse/epoch，不能与事故重复混淆。GFCR综述的Replay还覆盖缓存、前缀和其他产物复用，比训练经验池的含义更广；本书按实际对象分别说明，不把所有缓存都算成off-policy更新。[5]

## 相同权重不保证相同采样概率

考虑某个固定状态的一个动作：实际采样器μ给概率0.4，训练侧旧快照重算为0.5，当前策略为0.6。当前/旧ratio=1.2，而旧/行为=1.25，两者相乘才是该动作的当前/行为=1.5。长期参考π_ref是第四个职责，与这两个比值分别记录。

在同一两动作bandit中，若该动作奖励1、另一动作0，μ下期望奖励0.4，目标π下为0.6。完整支持下精确IS可以重构0.6；若把权重上限截为1.2，估计变成0.48，明确引入偏差。这是独立可枚举算例，不是多步语言模型的完整校正证明。

多步轨迹在相同初始分布和环境转移假设下，完整轨迹IS涉及各动作比值的乘积，方差可能很大。token校正、序列截断、拒绝采样等有各自权衡；“加了权重”不保证消除状态分布偏差，更不能补出μ从不产生的动作。[verl说明与数学推导](https://verl.readthedocs.io/en/latest/algo/rollout_corr_math.html)

| 检查对象 | 保留什么 | 最小核对 |
| --- | --- | --- |
| μ实际rollout | 采样版本、后端、精度、解码、实际logp | 固定动作重算差异；不覆盖原值 |
| π_old快照 | 训练侧旧logp、模板、mask | 本批更新期间保持固定 |
| π_current | 当前logp、优化器计数 | 与前两种ratio分别统计分位数 |
| 筛选/校正 | 权重、截断阈值、拒绝mask | 被拒条数、有效样本量和保留题目分布 |

对agent工作流还需把事件父子关系、工具版本和每个参与角色的权重版本带入队列。更新某个角色后重放旧团队经历时，后续协作者也可能改变；见[附录E](/postraining/07-appendix/e-agentic-multi-agent-rl/)。本节未部署异步框架，没有生产吞吐结果。

## 成本计数与显存

8题×每题4回答×平均100个生成token，是3200个生成token；优化时可能复用多次，前向/反向和参考/奖励评分又是其他计算。生成token/s、更新有效token/s和端到端题/s不应混报。日志应同时保留各阶段耗时和整体完成量，长尾长度用分位数而不是一个均值概括。

显存还可能含策略、参考/critic/奖励权重、优化器、训练激活和采样KV cache。LoRA只改变部分训练状态，不能消去所有这些项。先用目标硬件短跑采集分项证据，再选择并行、放置或offload；本站CPU例子不提供GPU MFU或吞吐门槛。

若actor使用BF16权重2字节、BF16梯度2、FP32主权重4、Adam一阶/二阶矩共8，则静态训练状态约16字节/参数；1B参数是16GB十进制，不含激活、通信buffer、临时重组、分配器与保存峰值。若梯度为FP32则变为18字节/参数，不存在对所有实现成立的固定常数。

同等规模的BF16冻结参考另需2GB参数；独立同规模critic若同样训练则再约16GB；冻结RM再2GB，四者合计36GB。若rollout另持一份actor权重再加2GB，以及它自己的KV。程序验证器、共享骨干、缓存logp或不使用critic会改变这些项，不能把“四角色”固定写成“四份相同模型”。

简单attention的KV存储可粗估为 `2×层数×并发序列数×已存长度×KV头数×头维度×元素字节`，前面的2是K和V。独立构造层数16、并发8、长度1024、KV头4、头维64、2字节，得到134,217,728字节=128MiB；不含分页碎片与共享前缀等实现差异。学习器激活和rollout KV不是同一个分项。

参数分片后也不能把36GB简单除以总设备数：冻结角色和rollout可能在另一个池里，临时all-gather、激活和KV的分布也不同。这是预算假设，不是显存实测。目标硬件短跑应测各阶段峰值与端到端接受吞吐。[RLHF Book实现讲义](https://rlhfbook.com/teach/course/lec4-chap6-p2/)

## 如何把性能与质量放进同一份报告

固定同一基座、任务和独立验收协议，分列：请求/完成/评分成功/保留/实际提交的轨迹数，生成token、学习有效token消费与成功更新数；再记录各阶段耗时、队列年龄、权重发布延迟和已分配GPU时。重复学习的56个目标位置不能冒充28个新生成位置之外的新数据。

prefill、逐tokendecode、反向更新和工具等待的瓶颈不同，GPU利用率或单kernel吞吐不能代替端到端效果。只有在质量与预算条件固定时，才比较“更快达到某个验收水平”。MFU须说明模型FLOPs口径、设备峰值与时间区间；RL混合多角色工作负载不能直接照搬预训练的一条MFU数字。本站没有测这些GPU指标。

> **一句话听懂**：版本、队列、长度与完成量是算法语义的一部分，编排不能只按设备数画图。

> **到这里，你应该已经能听懂：**“采样worker确认版本后，轨迹仍要保存实际actor身份。”
