## 从“知道答案”改成“自己取得答案”

单轮状态提取任务把`status=shipped`直接交给模型；工具任务只给订单ID，助手必须选择查询、读返回、再答复。新增的难点是**决策会改变后续能看到什么**。不查单就猜对一次，不足以证明策略会可靠取证。

```text
任务/订单表/权限/工具版本（环境）
             ↓ 只暴露允许的信息
观测历史h0 → 查询动作a0 → 返回观察o1 → 历史h1 → 答复动作a1
                  ↘ 错误/超时/预算耗尽            ↓
                              任务验收与终止状态
```

**agentic RL**在这里指用任务交互结果更新agent决策策略。一个固定提示词agent会调用工具，并不因此已经经过RL训练。[Agentic RL综述§2](https://arxiv.org/html/2509.02547v5#S2)提供状态、动作、转移、奖励的比较框架。环境全貌通常不可见；把可见历史h当策略输入，不等于证明真实世界在当前短上下文下满足Markov性质。

| 对象 | 工单中的具体内容 | 教学检查 |
| --- | --- | --- |
| 环境状态 | 订单表、权限、查询次数、是否完成任务 | 保存初始快照/版本，不能只保存最终文本 |
| 观察 | 用户问题、工具返回或异常 | 可进入后续上下文，通常不作为策略动作目标 |
| 动作 | 查询名与参数、答复、主动终止 | 保存实际动作token、actor身份和行为logp |
| 奖励 | 订单与状态正确、依据充分、调用成本 | 任务奖励与系统失败状态分开 |
| 边界 | 成功、真正失败、采样切段、超时 | 分别定义评分、mask和是否允许价值自举 |

## token、一次调用、一整条任务是三个单位

一个工具调用可由很多token组成；它也可以整体视为一个**宏动作**。固定上下文和模板时，调用的联合logp是属于该动作的生成token的logp之和。工具返回由环境产生，不能一起乘进策略动作概率。把整调用当一步，折扣γ就是“每调用一步”的约定；逐token建模则须重新对齐时间尺度和价值位置。

最低限度的轨迹契约可写为：

```json
{
  "episode_id": "order-A17-demo",
  "event_id": 2,
  "agent_id": "reply",
  "parent_event_ids": [1],
  "context_hash": "示意占位身份，实际运行应计算内容哈希",
  "actor_version": 10,
  "behavior_logp_kind": "actual-sampler-conditional",
  "action_mask_kind": "assistant-generated-targets-only",
  "environment_version": "orders-fixture-v1",
  "reward_version": "task-check-v1",
  "terminated": true,
  "truncated": false
}
```

这是字段示例，不是生产框架的可直接导入schema。真实记录还应保存上下文/动作数组、工具返回、异常、成本、解码设置和可解析的父子事件关系。展示用省略不能进入实际概率计算。[Agent Lightning §3.1–3.4](https://arxiv.org/html/2508.03680v1#S3)把执行记录与训练交接作为重要设计对象；记录接口通了仍须验证信用分配和更新目标。

## 为什么团队得1分，两个角色却不是同一个梯度

现在拆成两个决策者：查单员选择正确订单，答复员选择正确解释。先构造两个独立二动作策略，成功概率分别p=0.25、q=0.5；只有都正确才得1分，不考虑中间观察影响。这是可枚举的简化协作博弈，不是真实工单或语言模型结果。

| 查单员 / 答复员 | 错 | 对 |
| --- | --- | --- |
| 错 | 0 | 0 |
| 对 | 0 | 1 |

团队期望奖励J=pq=0.125。令各成功概率由各自标量logit经sigmoid得到，则：

$$\frac{\partial J}{\partial z_1}=p(1-p)q=0.09375,\qquad \frac{\partial J}{\partial z_2}=pq(1-q)=0.0625.$$

同一个终端分数仍能给两套参数不同梯度。把团队奖励给各动作可以构成合法的共同目标估计，但往往噪声大，不能把一次失败解释为所有角色同等犯错。答复员再好，查单错误也可能使团队失败；只看终端0分很难定位。

### 参数共享、集中训练、分散执行分别在说什么

- **独立策略**：查单员和答复员各有参数，轨迹记录两者版本。对方更新会改变自身所处的训练分布，是多智能体非平稳性的来源之一。
- **参数共享**：同一模型以role条件执行不同职责。可把多个角色的梯度累加到同一参数；角色数不等于权重份数。
- **CTDE（集中训练、分散执行）**：训练时的critic可使用更完整的联合信息，执行时actor只用允许的局部信息。是信息设计范式，不是一个固定优化器，也不保证任意通信受限任务都能使用同一实现。

这一信息区分可对照[MAPPO论文§3.2](https://arxiv.org/html/2103.01955v4#S3.SS2)的集中价值/局部actor与IPPO比较；它是2022年的基础资料，不是本轮选入的近期LLM多智能体实验。

多卡DDP复制同一个agent只是在并行计算；多个agent用固定提示词互相讨论只是在协作推理；只有实际定义并更新决策策略，才讨论相应的MARL训练。还要说明是共同奖励、各自奖励还是竞争目标。

## 反事实基线：固定上下文，换一个动作会怎样

想判断查单这一步，可以固定此前用户问题与权限，替换查询动作，然后按**同一套后续策略/环境规则**继续，比较任务结果。不能一边换查询，一边升级答复模型、改变订单表后，把差异全部算成查询贡献。

[C3 §2–3](https://arxiv.org/html/2603.06859v1#S3)研究固定上下文和后续分布下的局部反事实重放与留一法基线。借鉴其问题定义，独立构造四个等次数候选重放回报 `[1,0,1,1]`：

| 候选回报R | 其他三个的平均 | 留一优势R−其他均值 |
| --- | --- | --- |
| 1 | 2/3 | +1/3 |
| 0 | 1 | −1 |
| 1 | 2/3 | +1/3 |
| 1 | 2/3 | +1/3 |

本表只演示LOO算术，没有运行重放环境。C3的无偏性论述依赖其冻结上下文、采样与固定后续分布等假设，不能外推到任意线上聊天日志。重放不可逆工具、未保存的隐藏状态或不同后续策略时，反事实含义会变。候选生成、重放次数与评估器费用也须纳入预算。

<details>
<summary>为什么基线可以依赖别人的动作，却不能偷偷依赖正在优化的动作</summary>

在本节独立两策略例子中，记正确动作编号为1、错误为0，对查单员使用 `b查=p×a答`，即固定答复动作后对查单选择求期望；对答复员使用 `b答=q×a查`。这个基线依赖别人的动作，条件下却不依赖自己的采样动作，所以减去它不改变精确期望策略梯度。数值脚本枚举四种联合动作，确认仍得到0.09375与0.0625。

若把自身动作影响混进基线且不作相应修正，这个抵消理由就失效。真实序贯通信中，后面的动作可能已经依赖前面的动作，不能把本节独立策略公式原样套用；须用条件价值和明确的反事实采样协议。

</details>

## 怎样验收一个工具/多智能体实验

| 现象 | 需要的证据 | 最小验证 |
| --- | --- | --- |
| 团队分高，某角色只是复述答案 | 消息、可见信息、动作mask | 隐去不该提前出现的答案，检查是否依然成功 |
| 工具失败都被当作答错 | 执行状态与任务评分分列 | 固定一次工具异常，检查重试/退出/评分协议 |
| 新旧协作者混用 | 各角色actor版本、调度与环境快照 | 固定版本重放同一轨迹，不先调整学习率 |
| 反事实收益不稳定 | 前缀哈希、后续版本、重放次数 | 固定上下文和后续规则，只改变一个决策 |
| RL分数上涨，实际成本失控 | 全部调用、token、重试与墙钟 | 在同一预算下比成功率，保留失败样本 |

本书现在实际运行的是消息mask、两策略精确梯度和构造回报的数值夹具。没有训练工具型LLM、CTDE critic、真实多智能体协作者或C3；运行入口与产物见[6.3](/postraining/06-tools-practice/03-finite-action-rlvr/)。
