## 先对齐一张接口图

从[1.3系统架构](/postraining/01-system-overview/03-posttraining-system-architecture/)开始，标出自己负责的数据、采样、更新或评测。先说清接收什么、交出什么、版本和单位是什么，再选择框架。

| 负责范围 | 重点阅读 | 做一次什么检查 |
| --- | --- | --- |
| 数据 | 2.1–2.5 | 组划分、真实模板、回答mask与评分反例 |
| 算法/训练 | 3.1、3.4、4.1–4.4 | sum-logp、冻结参考、old概率、组方差 |
| 平台 | 4.1、5.4、6.4 | actor版本、结束原因、队列与恢复边界 |
| 评测/交付 | 5.1–5.5、6.5 | 固定条件、原始输出和结论范围 |

## 先跑通，再定位

RL专项按[数据/目标地图](/postraining/00-reading-guides/06-rl-map/) → 4.1 → 4.2 → 5.4检查实际采样分布与训练旧快照，再用[附录E](/postraining/07-appendix/e-agentic-multi-agent-rl/)核对agent事件、角色版本和信用分配。10份重点资料见[附录F](/postraining/07-appendix/f-rl-reading-list/)。新增rl_mechanisms.py只做CPU数值检查，不要求安装verl等生产框架。

按[6.1环境](/postraining/06-tools-practice/01-environment-and-artifacts/)准备Python，完成6.2的SFT/DPO，再运行verify。重点观察：同样本的mask、DPO初始ln2、参考未更新、同边界恢复完全一致。不要因为loader成功就假定数据和概率语义正确。

生产框架接口可沿原始论文/官方材料阅读，但本项目没有运行verl或多GPU。读5.4时用版本表和交接物理解拓扑，不把角色数量等同设备数。

## 使用本路线的提问视角

从[1.3进入本路线](/postraining/01-system-overview/03-posttraining-system-architecture/?reader=engineer)，节首默认展开对应角色的问题；也可用选择器切换。需要补概率与梯度时读[必要基础](/postraining/00-reading-guides/05-essential-foundations/)。工单助手的单轮到工具轨迹接口见[4.1](/postraining/04-online-rl-distillation/01-rollout-and-policy-versions/)，已有基座实践见[6.2](/postraining/06-tools-practice/02-offline-sft-dpo/)。

## 系统贯穿路线

沿1.3 → 3.3 → 4.2 → 5.4 → 6.4跟踪同一个批次：目标分母、梯度归约、成功更新、权重发布与checkpoint提交是五个不同检查点。新增12参数生命周期与固定PPO窗口的两rank CPU测试可核对这些接口；未运行多GPU/生产框架。需要先补G/V/Q/A时读[RL基础](/postraining/00-reading-guides/07-rl-foundations/)。
