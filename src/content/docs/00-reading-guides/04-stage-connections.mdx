## 目标改变时，先决定哪些状态继续

本页把1.3的学习入口与5.4的执行系统连接起来。先给阶段写清**接收哪份模型、改什么行为、交出哪些证据**，再谈跑多少卡。学习方法不是只能依次通过的关卡：SFT或DPO可以结束一个项目，RL也可产出新的示范再进入SFT，教师蒸馏可以从不同阶段分支。

生产基座 → 任务定义与数据 → 可选SFT / 偏好 / 在线RL / 蒸馏 → 每阶段验收，这是一张选择图，不是必经recipe。阶段名称如mid-training在不同项目中用法不一，不能仅凭名称判断监督和优化目标。

| 交接 | 继承什么 | 重建/冻结什么 | 新报告绑定什么 |
| --- | --- | --- | --- |
| 基座→SFT | 模型结构、权重、tokenizer | 新数据、回答mask、优化计划 | 基座/模板/数据/环境 |
| SFT→本书DPO | 同份SFT权重 | 新AdamW/计数/RNG，冻结SFT参考 | 偏好对、β、参考身份 |
| 策略→在线RL | 合适的初始策略 | 行为快照、奖励/优势和版本协议 | 采样、评分、更新与队列 |
| 任意阶段→严格恢复 | 该运行的完整状态 | 不私自换目标或参考 | 同代码/数据/计划/环境 |
| 学生→OPD | 学生权重与采样能力 | 教师反馈协议与新目标 | 教师/学生/前缀/损失方向 |

表中“新DPO重建优化器”等是本项目明确采用的阶段约定，不是所有生产项目都必须丢弃优化器；若决定继承，应把兼容条件和计划写进新阶段manifest。只有加载参数，不能声称继承了原运行的全部状态。

## 用同一份阶段契约串起数据、算法和系统

| 阶段 | 先确认的行为缺口 | 学习与数据契约 | 执行系统的新增责任 | 验收后交给谁 |
| --- | --- | --- | --- | --- |
| 基座→SFT | 不会按约定格式或工具协议输出 | 示范、回答mask、有效位置计数 | 批量训练、参数/优化器和数据版本 | 满足格式与回归条件的策略 |
| 偏好数据→RM / DPO | 有多种写法但比较标准不明确 | 同题比较；RM拟合标签或DPO优化相对参考 | RM分支另有训练/评测；DPO固定参考/缓存身份 | 评分器，或偏好更新后的策略 |
| 策略→RL | 自己采到的经历暴露决策错误 | rollout、奖励/状态、优势与选定归约 | actor/learner交接、队列、权重发布、数据年龄 | 新策略与完整训练状态 |
| 教师/强策略→学生 | 行为需转移或降低运行成本 | 指定轨迹与教师反馈、词表/散度 | 教师评分、缓存/采样成本、信息隔离 | 学生权重和原行为保留评测 |
| 任一阶段→接受/回退 | 判断结果是否真正满足目标 | 冻结任务、生成协议和独立验收 | 报告绑定checkpoint，不混最新别名 | 接受版本或下一轮实验设计 |

“不会采到成功行为”与“能采到但概率太低”可能要求不同数据与探索支持；“一阶段提高、下一阶段丢失”又是交接/保留问题。近期[统一后训练综述§3与§6](https://arxiv.org/html/2604.07941v2#S6)提供了分析视角；它不是某个固定recipe的优越性证明。本书按任务证据选择阶段，不把所有后训练都硬归成同一种RL。

### 一份manifest至少把哪些身份绑在一起

```text
run_id / stage_id / parent_checkpoint_hash
architecture + tokenizer + template + train/eval dataset versions
objective + reduction + reference/teacher/reward identities
precision + parallel layout + optimizer/scheduler plan
actor successful updates / critic updates / rollout rounds / sampled + reused targets
checkpoint boundary + queue/replay policy + independent evaluation protocol
```

这些是字段职责，不是强制采用某个框架schema。数据和评分器能单独升级；升级后若改变了原目标，应另建阶段或明确迁移，不让旧缓存静默混入。检查点记录训练状态，阶段manifest记录它为什么这样训练，两者一起交付。

## 把节奏放在同一张表

先看本书已有的两类独立实验，避免把它们误串成同一个LLM端到端成绩：

| 发生点 | 本地语言模型例子 | 在线有限动作例子 |
| --- | --- | --- |
| 数据冻结 | 77 train / 23 val，组哈希划分 | 12题×4候选，规则冻结 |
| 每批/每轮 | 8示范或8偏好对 | 每题8次采样，96动作 |
| 参数更新 | 每批一次 | 每轮两次，old logp固定 |
| 阶段边界 | SFT300→新DPO120 | 80轮，160次更新 |
| 保存与验收 | 更新边界保存，固定23题生成 | 完整rollout轮边界保存 |

数值是本项目运行配置；语言模型与表格策略是两项独立实验，不能串成同一个“大模型完整RL流程”。验证反馈决定是否另做实验，不对当前权重自动反传。

另有[6.4的生命周期夹具](/postraining/06-tools-practice/04-stage-handoff-and-resume/)专门追踪同一张12参数表格策略跨SFT/DPO/RL的状态交接。它演示阶段身份、优化器重建、固定参考、采样版本、批次提交和边界恢复，不替代上面的真实小语言模型或已有基座实验。SFT/DPO/RL阶段各自的更新数不能不加stage_id直接比较。

## 两种反馈，不同的负责人

```text
训练内：固定任务/评分定义 → 采样/组批 → 优势/损失 → 参数更新 → 新采样
实验间：独立验收报告 → 定位行为缺口 → 改数据/任务/目标 → 建立新运行
```

前一条由算法与训练系统共同保持数值和状态语义；后一条由任务负责人据证据选择下一步。若把dev上的每次试验都当最终test结论，或把评分器优化当用户质量，管线再顺畅也无法支持结论。5.1–5.5围绕这条验收链展开。

## 公开实例怎样读

[InstructGPT](https://arxiv.org/html/2203.02155v1)展示示范、偏好与PPO的具体组合；[DeepSeek-R1](https://arxiv.org/abs/2501.12948)展示包括冷启动、RL与其他阶段的项目设计。两者的数据、目标和约束不同，不能抽出一个顺序当通用最优。

本书只复现声明的小型机制；不复用其模型成绩，不将未运行的OPD、语言模型GRPO或生产编排填作结果。

## 衔接到真实任务

先用[必要基础](/postraining/00-reading-guides/05-essential-foundations/)接上概率与梯度，再沿2.3→3.4比较显式奖励模型与直接偏好目标。工单应用从6.2已有基座的单轮状态提取，扩展到4.1的工具动作/观察方案；后一部分尚未运行完整语言模型训练，不能把前者6/6继承为工具成功率。
