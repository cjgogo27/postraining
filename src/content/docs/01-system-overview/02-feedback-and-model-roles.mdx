## 现场问题

## 同一道题，三种监督

取 prompt 为“2+3，只输出数字”，以下数据均是说明接口的人工例子：

| 信号 | 一条记录 | 提供的信息 | 没有提供的信息 |
| --- | --- | --- | --- |
| 示范 | 回答 `5` | 这些 token 应如何续写 | 其他有效解答的相对质量 |
| 成对偏好 | `5` 优于 `6` | 对此 prompt 的相对排序 | 一个可跨任务比较的绝对分数 |
| 可验证奖励 | 完整输出恰为 `5` 得1，否则0 | 此次输出是否满足验收规则 | 每一步为什么错 |
| 过程反馈 | 第一步化简正确、第二步计算错误 | 中间步骤的局部信息 | 后续整体策略一定可靠 |

**RLHF**描述使用人类反馈的训练范式，**RLVR**强调奖励可被规则或执行结果验证；**PPO/GRPO**是更新策略的方法。它们不是同一层面的备选缩写。PPO可以使用可验证奖励，GRPO也可接奖励模型，而不是只会做数学。[1][2]

## 同名“模型”，职责不同

当前策略 $\pi_\theta$ 参与更新；旧策略 $\pi_{old}$ 记录“这一批轨迹由谁产生”，在复用这批数据时保持固定；参考策略 $\pi_{ref}$ 用来约束漂移，常比旧策略保留得更久。奖励模型把回答映射成分数；价值模型/critic估计未来回报，标准PPO常用它估计优势。验证器可能只是程序，不需要神经网络。

这里先假设旧快照与实际采样分布一致。若采样后端、精度或解码使行为分布μ与训练侧π_old不同，两份logp应分开保存；[4.1](/postraining/04-online-rl-distillation/01-rollout-and-policy-versions/)和[5.4](/postraining/05-evaluation-diagnosis/04-training-rollout-orchestration/)会拆开这个接口。单轮、工具型agent和多智能体是任务结构；在线/离线是采集条件；不要把它们与算法名混成一列，见[RL地图](/postraining/00-reading-guides/06-rl-map/)。

| 对象 | 训练中是否通常求梯度 | 应保存或关联什么 |
| --- | --- | --- |
| 当前策略 | 是 | 权重、优化器、步数 |
| 旧策略快照 / old logp | 否 | 采样版本、采样设置、动作概率 |
| 冻结参考策略 | 否 | 权重身份、tokenizer与模板 |
| 奖励器 / 验证器 | 策略更新时通常不对它反传 | 评分版本、输入、状态、输出 |
| critic | 标准PPO中单独训练 | 价值预测、目标、优化器 |

“需要四种职责”不等于“需要四台GPU或四份完全独立权重”。有的职责共享基座、有的缓存logp，有的完全不需要critic。框架对象名也不能代替职责核对。

## 怎样发现信号错位

如果 chosen 与 rejected 使用不同prompt，比较可能测的是题目难度；如果奖励记录只留1/0而丢了超时状态，训练会把基础设施故障当成答错。先用十条样本逐项追踪ID、模板、输出、评分版本，再扩大规模，比先改优化器更能排除接口错误。

> **一句话听懂**：示范给写法，偏好给比较，奖励给结果；信号来源与优化算法要分别说明。

> **到这里，你应该已经能听懂：**“old绑定采样版本，reference绑定漂移基准，别共用一个会变的身份。”
