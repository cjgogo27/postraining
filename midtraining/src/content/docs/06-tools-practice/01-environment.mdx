## 最短路线：从仓库根目录执行

```bash
python -m venv .venv
```

Windows PowerShell激活：`.venv\Scripts\Activate.ps1`；Linux/macOS为`source .venv/bin/activate`。已有合适环境也可直接使用。执行前检查`python --version`和当前解释器路径，避免把依赖装到另一个Python。

```bash
python -m pip install -r midtraining/examples/requirements.txt
python midtraining/examples/lab.py --out runs/my-midtraining
python midtraining/examples/verify.py --out runs/my-midtraining-checks
```

默认lab安装依赖后不下载模型、不访问外部语料或API。已验证环境为Windows11、Python3.12.5、torch2.11.0+cpu、FP32、CPU单线程；这些命令是重跑入口，不表示本轮重新创建过虚拟环境或安装所有依赖。

## 每个命令应该交出什么

| 命令 | 产物 | 成功条件 | 常见失败 |
| --- | --- | --- | --- |
| lab.py | corpus.json、report.json、各阶段.pt | 退出0，两个seed区组、源计数正确、loss有限 | out非空、依赖/内存问题 |
| verify.py | report.json、恢复夹具.pt | 12项PASS，包含实际源码变化拒绝 | 环境不同、源码或计划不匹配 |
| 可选adapt_pretrained.py | 报告、adapted模型目录 | 三支固定预算及重载对照通过 | 无缓存、下载失败或内存不足 |

out目录非空时lab拒绝覆盖。权重和大日志留在被Git忽略的runs中；发布小JSON、原始语料、命令和身份。恢复夹具含Python序列化，仅加载可信文件。

## 每一步先看什么，再继续下一步

```text
解释器/依赖 → verify通过 → lab生成独立目录
           → 固定报告计数 → 原始输出 → 新诊断/性能时间线
```

`ModuleNotFoundError`先核对当前python和pip是否同环境；`out`非空是防止覆盖旧证据，换新目录而非删旧报告；源码身份不匹配时先确认是否切换了版本，不能手工改checkpoint哈希强行恢复。完整流程不要求输出漂亮答案，要求检查对象与结果能对上。

默认脚本只依赖torch/NumPy。公开基座另用Transformers/HF Hub；下载开关应显式提供。绘图的matplotlib是可选依赖，不应为了跑最短训练路线而安装生产平台。

## 新增CPU profiler：看人工区间怎样包住算子

```bash
python midtraining/examples/profile_cpu.py --out runs/my-midtraining-profile
```

本轮实际CPU单线程、FP32，两次预热更新后记录四次更新/512目标。人工区间的inclusive CPU累计时间如下，单位毫秒，**不是每步延迟或无记录器吞吐**：

| 区间 | 实际调用数 | CPU总时间ms |
| --- | --- | --- |
| mid/data | 4 | 8.3071 |
| mid/forward_loss | 4 | 13.9073 |
| mid/backward | 4 | 18.9149 |
| mid/clip_update | 4 | 27.2867 |

产物为`report.json`与Chrome trace格式的`trace.json`，后者可用支持该格式的时间线查看器打开。本轮验证文件可解析并含四类人工区间；不声称已经在某个时间线UI中人工拖拽检查。记录器有开销，算子行与人工父区间不能重复相加；四次短跑也不足以给优化器性能排名。

该脚本使用新随机模型、固定lr0.001做标注示范，没有继承真实base、没有执行原lab评测/保存，也没有替代原来96更新的配比实验。[Profiler官方API](https://docs.pytorch.org/docs/2.11/profiler.html)定义了区间、活动和时间选项，解释结果时要保留CPU/GPU与inclusive/self的区别。

> **一句话听懂**：先让最小命令产出可追溯记录，再扩大模型和系统复杂度。

> **到这里，你应该已经能听懂：**“这份报告绑定了环境和代码，权重留在独立运行目录。”
