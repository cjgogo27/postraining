> **系统位置**：接收需求，交出固定任务与回退协议，进入[1.3的数据入口](/postraining/midtraining/01-system-overview/03-midtraining-system-architecture/)。

## 文档很多，问题还没有定

团队说有一百万页维修资料。评测同事却问：模型要预测故障码、总结过程，还是引用具体页码？这三件事需要不同的样本与验收。

## 用一张任务卡固定对象

| 字段 | NX教学任务中的取值 | 真实项目需要再补什么 |
| --- | --- | --- |
| 输入 | 型号、故障码前缀 | 文档时间、权限、可用工具 |
| 目标 | 续写对应标签 | 任务定义与可接受措辞 |
| 验证划分 | 新实体ID，模板和映射共用 | 新模板、新时间和新主题 |
| 主指标 | 固定窗口NLL及原始续写 | 独立业务test与人工复核 |
| 保留项 | GX通用文本NLL | 通用任务、安全和输出协议 |
| 停止/回退 | 保留完整预定终点 | 事前确定的约束与预算 |

默认实验只适合观察概率和数据分布的变化。即使标签输出全对，也不能宣称掌握维修知识；标签本来只有四种，且模型没有真的操作设备。

## 验证集负责选方案，测试集负责最后确认

如果反复查看一组题并按分数改配比，这组题已经参与了方案选择。它仍可用于开发，却不再是完全独立的最终能力证据。生产评审应另留一次性test，保存题目与评分器身份；不能把第一次没看过的题在看了十次以后仍叫“盲测”。

本书小实验只有固定验证探针，明确没有独立产品test。两个seed是运行区组，16个窗口不是16个独立模型重复；重复统计同一模板不能代替更广的任务覆盖。

## 用失败类型反推数据需求

若错误主要在术语映射，先检查相关文本与版本；若在跨段证据，增加距离和干扰受控的探针；若只是不按JSON输出，不能仅靠再喂原始手册解决。训练数据应服务于能区分解释的任务，而不是按文件大小证明努力程度。

## 把“维修场景”写成可交接任务卡

可以先完成一张自编示例卡，而不是先收齐所有文档：

```yaml
task_id: nx-version-grounding-v1
input: 两版文档、型号、故障码、允许采用的时间范围
output: 最新有效标签及原文定位；证据冲突时说明冲突
split_key: 文档家族与实体；另留未来时间段
primary: 标签与版本联合正确率
secondary: 引用定位、格式有效、证据不足处理
retention: 固定旧任务组的逐项变化
```

这是设计模板，不是本轮执行过的任务。这里把“最新有效”写进题目，是为了避免模型按训练频率选择旧版本；把文档家族作为组，是为了避免同一手册修订版跨越train/test。

## 数据不足与指标不敏感，表现可能相似

某类错误只有3道题时，多答对1道就变化33.3个百分点。若用这些题挑配比，一次偶然输出会显著影响选择。先增加错误类型覆盖与固定样本，再讨论更多token是否值得；不要把小分母导致的波动解释为训练稳定性差。

可以将交付拆为三个门槛：数据身份可复核、训练与评测协议可复跑、任务收益满足事前约束。前两个通过说明工程链条完整，不自动让第三个通过。本书默认0/4正好展示了这一区别。

进一步阅读[DAPT论文§4任务适配](https://arxiv.org/html/2004.10964v3#S4)：任务附近的文本与宽领域文本不是同一个数据对象。它不能替项目决定真实任务的验收阈值。

> **一句话听懂**：数据预算之前先写清“哪些输入下，什么输出算进步，哪些旧行为不能退”。

> **到这里，你应该已经能听懂：**“这组验证题用来选配比，最终交付还需要独立test。”
