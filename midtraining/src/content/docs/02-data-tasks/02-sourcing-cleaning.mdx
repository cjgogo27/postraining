## 一个清洗规则删掉了关键关系

PDF里的Z0与解释分在两列。抽取器按行拼接后，标签跑到了下一型号；随后“删除短行”的规则又把Z0删了。文件能打开、token数充足，却已经不再表达原手册。

```text
source_id / source_version / permission
  → raw_sha256 → parser_version → cleaning_rules
  → normalized_document / group_id / rejected_reason
```

至少保留原文定位、解析/清洗版本和拒绝原因。页码、表格列、代码缩进、公式上下标在某些任务里就是内容，不能按所有网页相同的规则处理。

## 用几条反例验收规则

| 输入现象 | 可尝试的处理 | 需要看什么反例 |
| --- | --- | --- |
| 每页相同版权页脚 | 按来源模板移除 | 同样短的故障码不能被删 |
| OCR的O/0或l/1混淆 | 校验字段/词表、保留原图定位 | 不把合法型号强改为常见词 |
| 表格错列 | 重建行列与关联 | 原始型号—标签关系是否还相同 |
| 多版本互相矛盾 | 明确时间与版本，不盲目拼接 | 旧说明是否覆盖了新说明 |

启发式、语言识别、质量模型各能提供不同筛选信号；任何“高质量分”都不能替代来源抽检。按来源和错误类别分层抽样，比只看最终平均长度更容易发现系统性损坏。

## 来源可见，不等于获准训练

公开可下载、允许内部阅读和允许训练/再分发不是一回事。记录许可证、使用范围、敏感信息处理和撤回方式；需要组织授权判断时，以实际资料和流程为准，不凭一个URL推断权限。

本站语料由程序原创生成，不抓取真实手册、用户数据或外部API。它没有运行生产OCR、语言识别或质量分类器；上述是设计与验收方法，不是本站清洗成绩。

## 从一个损坏样本看清洗顺序

假设原文两行是`Z0 -> luma`和`Z1 -> nexo`，OCR后变成`ZO -> luma Z1 -> nexo`。先做空白规范化不会修复型号；直接将所有O改成0又会损坏正常单词。应保留原始页与坐标，先识别字段，再仅在受约束字段里提出修正，并留下原值、改值与规则ID。

一份最小审计记录可以长这样：

```text
doc_id=nx-0042；raw_hash=…；parser=v3；rules=nx-clean-v2
change: field=code；before=ZO；after=Z0；reason=known-code-review
review: accepted；source_page=7；normalized_hash=…
```

省略号表示示意字段，不是假造哈希。真实manifest应保存完整值。对于无法确认的行，拒绝或隔离比猜一个最常见标签更容易追查。

## 质量、相关性和难度不要共用一个分数

语法整齐的广告可能质量模型打分高，却不相关；专业推导可能低频、难预测，却是任务所需；乱码也可能有很高loss。先分别记录可读性、来源可靠性、任务相关性、重复与版本，再决定过滤或上采样。把所有高loss文本上采样，可能反复训练损坏数据。

[OLMo 3 §3.4](https://arxiv.org/html/2512.13961v2#S3.SS4)区分解析、启发式、去重及分类等步骤。借鉴的是把处理职责拆开，并通过消融和抽检验证，而不是抄一个阈值就称适合维修资料。

建议每次规则变更保存输入/接受/拒绝数量、token量及按错误类别抽取的对照样本。拒绝率上升既可能是过滤更有效，也可能是误删更多，不能单凭该数值判好坏。

> **一句话听懂**：清洗输出既要有文本，也要有能追溯和复核转换的身份。

> **到这里，你应该已经能听懂：**“先抽检型号和表格关系，再接受这个清洗版本。”
