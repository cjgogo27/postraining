## 同一条解答，三种训练方式

数据里写着“先查Z0，再映射luma”。训练同事说加入了推理数据，另一位同事便把实验登记成RL。其实记录出现步骤，不等于优化器用到了奖励。

<SectionQA id="3.2" mode="ask" />

| 使用方式 | 输入对象 | 实际优化信号 |
| --- | --- | --- |
| 文本继续训练 | 包含步骤的文档或序列 | 下一token交叉熵 |
| 回答监督SFT | 问题、示范步骤与回答 | 约定回答位置的交叉熵 |
| RL | 策略采样的步骤/回答及评分 | 由回报/优势构造的策略目标 |

来源、序列格式、mask和梯度决定它属于哪种实现；“数学”“代码”“推理”只是内容类别。中训练也可能混入指令样式的数据，不能把没有chat template视为唯一判据。

## 数据质量对应到可检查对象

代码要看仓库/许可证、生成文件、重复样板、依赖和测试协议；数学要看答案抽取、题解一致性、符号损坏与评测污染；推理轨迹要看教师版本、验证方式与格式依赖。程序执行通过只检验规定测试，不能把未覆盖路径算作正确。

例如一个代码样本有5个测试，只覆盖正数；模型学会同样的捷径后，在负数输入失败。此时训练token增加，不会自行补出缺失的任务覆盖。应把“语法通过、样例通过、隐藏测试、未见问题”分别记录。

## 公开项目给出的是条件化做法

Olmo 3的中训练混合包含多个能力来源；SmolLM3也公开描述了推理适配和后续SFT的关系。[1][2] 它们说明阶段可以围绕能力准备组织，但不证明任意模型都应按同样比例加入同样轨迹。

本书没有下载这些推理集或运行真实数学/代码中训练。默认NX标签任务只用于数据—概率—回退的机制练习，不能宣传成推理能力结果；想扩展时先按2.1建立独立任务与污染协议。

## 代码样本要能追踪到仓库级对象

假设训练里出现函数`map_tag(code)`和单测文件。按文件随机切分可能把同仓库的函数定义放入训练、调用和测试放入验证；模型可依赖共享标识符，未必解决新问题。先按仓库/派生关系分组，再区分正文代码、自动生成文件、文档和测试。

代码目标还可能采用FIM：把缺失片段放到特殊布局，让模型根据前后文补中间。它改变序列组织和特殊token，不是给普通因果mask加入未来可见。普通训练、FIM与后续任务提示的格式都应随manifest记录。本书并未实现FIM。

## 数学题的“答案对”与“过程可用”是两层审核

自编例：题问“2个组件，每个3个端口，共多少”，答案写6，过程却说`2+3=6`。答案抽取器会通过6，过程包含错误；只按答案过滤会保留这种轨迹。反过来，等价表达`6.0`被严格字符串匹配判错，又是抽取协议问题。保留题目、教师原输出、验证器、抽取结果和接受原因，才能区分两类错误。

教师产生更多样本不代表获得更多独立知识；同题改写、重复思维模板和评测题族都可能放大相关性。先建立题族/来源组和隐藏测试，再测数据规模效应。

[SmolLM3官方Reasoning Mid-training](https://huggingface.co/blog/smollm3#reasoning-mid-training)采用含推理轨迹的序列来准备后续阶段；[OLMo 3 §3.5.2](https://arxiv.org/html/2512.13961v2#S3.SS5.SSS2)提供不同能力来源实例。应记录其数据形式与后续验收，不以“有思维链”推出已经做RL或已学会可靠推理。

> **一句话听懂**：先区分数据的内容、形式和优化信号，再讨论它如何帮助能力适配。

> **到这里，你应该已经能听懂：**“这轮用推理文本做因果训练，还没有在线奖励优化。”
