## 曲线不平稳，可能先是供数不平稳

手册缓存未命中时，loader等远端存储；稍后又连续取到同一来源。GPU利用率曲线和loss一起抖动，不能仅凭二者相关就判断学习率过大。

<SectionQA id="4.5" mode="ask" />

```text
唯一语料 → shard/缓存 → 预取队列 → 已计算批次 → 已成功提交更新
           I/O状态      队列位置     可能未提交       预算与恢复锚点
```

预取过的数据不等于已学过，完成反向也不等于参数已成功更新。故障后如果把预取游标当提交游标，可能跳过未训练样本；反之可能重复消费。应把逻辑样本/窗口身份与物理worker分配分开。

## 调度分三层理解

资源调度器分配设备与拓扑；launcher建立进程、rank与通信组；训练应用恢复模型、优化器和数据计划。重启进程不自动恢复应用状态。弹性改变成员时，还要重新定义DP、全局批量、分片状态和数据游标。

例如固定TP2/PP2/CP2，16→8设备会让DP2→1；若B/S不变，为保持源目标/更新，A需加倍。这个算例只是准入与计划设计，没有证明该模型能跨布局加载状态。本书严格resume直接拒绝world size变化。

## 日志把性能和学习接在一起

| 记录 | 用来区分什么 |
| --- | --- |
| 各源目标/更新与唯一数据量 | 配比兑现、重复消费 |
| I/O等待、队列深度与缓存命中 | 供数瓶颈、背压 |
| 通信/前后向/保存时间 | 计算还是同步在限速 |
| 成功更新、重算、丢弃、恢复位置 | 设备忙与有效进度的区别 |
| 配置/代码/权重/数据身份 | 运行是否可比较 |

吞吐要带分子：源token/s、含padding计算位置/s或端到端完成量/s；不能把评测和故障回放从成本中悄悄抹去。MFU若以模型约定FLOPs计，和含重计算等实际执行量不是一个口径。

本地lab串行供数，没有缓存服务、生产调度器或异步检查点。日志示意不替代性能剖析；任何GPU吞吐和费用都需目标硬件实跑。

## 同一组日志怎样区分三种慢

自编现象：四个rank里一个等数据，其余三个在通信处等待。只看其余rank的通信时间，很容易说“网络慢”；真正原因可能在那个rank的I/O。应关联同一次更新的各rank时间线，找最先阻塞的依赖，而不是把所有等待都当作通信服务本身的代价。

```text
rank0: 数据慢 ─────────→ 前后向 → collective
rank1: 数据 → 前后向 → 等rank0────────→ collective完成
```

另一个情况是每隔固定更新保存检查点时变慢；第三个是长样本导致前后向本身变慢。按数据/前向/反向/归约/更新/保存打标后，才能分别检验。异步重叠时，各段时长不能简单相加当作端到端总时间。

## 本书新增一个真正可运行的CPU时间线

```bash
python midtraining/examples/profile_cpu.py --out runs/my-midtraining-profile
```

两次预热更新后，记录四次更新、512目标，输出四个人工区间及`trace.json`；见6.1的实测表。没有GPU、外部loader服务或通信。它示范怎样把算子放回职责，而不是给TinyBase提供生产吞吐排名。

[torch.profiler 2.11](https://docs.pytorch.org/docs/2.11/profiler.html)能记录活动、形状与用户区间；`with_flops`也只是对部分算子用公式估算，不能把其总和当硬件实际全部FLOPs。记录器本身有开销，正式性能结论需关闭或控制这些开销。

## 弹性准入需要恢复的是逻辑工作

一个更新提交后，下一次逻辑窗口应从记录的计划继续；物理rank变化不应自动重置整条数据流。[torchrun重要说明](https://docs.pytorch.org/docs/2.11/elastic/run.html#important-notices)提醒重启后RANK和WORLD_SIZE可能变化。调度器负责资源，应用仍要定义重分片、未提交批次重放、全局分母与学习率进度。能重新启动不等于能够等价续训。

> **一句话听懂**：资源被使用、批次被计算、更新被提交，是三个不同的进度。

> **到这里，你应该已经能听懂：**“恢复锚点要用已提交游标，不能直接拿预取队列位置。”
