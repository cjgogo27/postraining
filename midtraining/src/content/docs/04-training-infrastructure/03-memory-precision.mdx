## 2GB权重为什么不等于2GB训练显存

假设1B参数、BF16权重占2GB（十进制字节）。训练还可能需要梯度、FP32主副本、Adam一二阶状态、激活、通信缓冲和临时张量。只看权重文件大小，不能判断是否装得下。

<SectionQA id="4.3" mode="ask" />

| 静态对象（假设一种混合精度Adam实现） | 字节/参数 |
| --- | --- |
| BF16权重 | 2 |
| BF16梯度 | 2 |
| FP32主副本 | 4 |
| FP32一阶/二阶状态 | 8 |
| 合计 | 16 |

这是有明确假设的静态16GB算例，不含激活与缓冲。某些实现梯度为FP32、没有独立主副本或状态被分片/offload，数字会变。GiB还要除以2³⁰，而不是10⁹。

## 计算换存储，不是计算消失

activation checkpointing保存更少中间激活，在反向时重算；减少峰值激活存储，却增加执行计算。offload把状态移到CPU/存储，引入传输与排队。更省显存不保证端到端更快，应记录同一任务下的更新时间和内存峰值。

普通attention的S²代价也不能靠减半B全部抵消。先用目标硬件短跑校准实际峰值、吞吐和等待，再调整B/S/A，而不是从纸面字节推一个固定安全batch。

## AMP更新边界要写完整

典型顺序是清梯度、autocast前向、缩放loss并反向、累积和必要同步、unscale、裁剪、尝试optimizer step、更新scaler。调度和已提交目标/更新计数应与**实际成功更新**协调；溢出跳过时，不应在未说明的情况下仍消耗一个学习率步。[1]

BF16范围和FP16不同，不代表BF16永不溢出；FP8还依赖缩放、算子和硬件实现。DDP完整副本的常规裁剪与分片参数的全局范数裁剪不同，应使用对应并行框架的正确语义。本书CPU FP32未运行AMP、重计算、offload或GPU显存测量。

## 预算表里哪些量随B、S或参数量变化

| 对象 | 一个简化尺度 | 优先尝试的控制 |
| --- | --- | --- |
| 参数/梯度/Adam | 与参数量N有关 | 分片、精度、offload |
| 残差与FFN激活 | 近似随B×S×层数增长 | 微批次、重计算、并行 |
| 显式attention分数 | 近似B×头数×S²×层数 | 内核、上下文切分、重计算 |
| 临时/通信缓冲 | 由实现与分组决定 | 实测峰值、bucket与重叠 |

这些尺度用来定位，不是精确显存公式。假设1B静态16GB约14.90GiB；标称24GB卡还要核对其实际可用容量、进程占用、缓存和碎片。静态状态“能放下”只是开始。

## 把优化器更新画成不可拆错的边界

```text
所有微批次：autocast前向 → 按同一分母scale(loss).backward
最后同步完成 → unscale一次 → 全局语义正确的clip
尝试step → 更新scaler → 确认成功与否 → 提交计数/调度/保存
```

累积中途unscale，再把后续scaled梯度加进去，会混合两个尺度；重复unscale也不正确。[AMP官方示例](https://docs.pytorch.org/docs/2.11/notes/amp_examples.html#gradient-accumulation)明确要求按有效批次边界处理。FP16中GradScaler可能跳过更新，因此数据已读/已计算目标与成功提交目标要分开记。

要特别区分：普通DDP每个副本拥有完整梯度时，可按约定对完整范数裁剪；FSDP/ZeRO等分片场景的本地范数只是一个分片，直接照搬本地clip不能保证全模型范数正确。使用所选框架支持的全局裁剪路径，再用小例核对。

> **一句话听懂**：显存要算状态与激活，精度和重计算要同时写出数值、计算与计数代价。

> **到这里，你应该已经能听懂：**“16字节只是假设静态状态，还没算长窗口激活。”
